# v1.1.4 Gen UI 状态观察验证

验证日期：2026-10-21。环境：本机 Darwin，mise 指定 Node 24.14.0、libuv 1.51.0。
全部实验使用隔离测试入口和合成临时目录，不访问个人状态或生产服务。

## 发布决定与行为边界

采用项目现有 chokidar，每个 storage 实例、scope 目录只有一个 watcher entry 和一个
ready Promise。Darwin 明确使用 stat polling，`interval`、`binaryInterval` 均为 500ms；
Linux/Windows 保持 native。两种后端不并行，也不在失败后切换。

get/observe 等待初始 ready；初始化错误拒绝等待调用方，dispose 关闭 watcher 并拒绝
未完成初始化，迟到 ready 不恢复已释放的实例。完整快照仍通过既有文件锁和原子替换提交，
既有 publish 队列串行读取并按值去重。set 的 ACK 通知保持即时；外部变化传播最新采样
快照，不保证捕获两次采样之间的每个瞬态值。约 500ms 是采样间隔，实际延迟还包含 IO
和调度耗时，不构成严格的端到端时间上限。

主任务已接受下述 8 scopes × 每 scope 100 条记录的实测开销。本次不增加 scope LRU、
公开 API、第二份状态事实或新依赖；不使用 sleep、自动重试掩盖初始化时序。
行为合同见 [状态观察方案](../specs/gen-ui-state-observation.md)。

## 原生漏事件证据

原始实现先等待 get 完成，再订阅变化，然后通过另一实例提交外部写入，仍在 24 轮独立
进程验证中出现 3 轮原 30 秒超时。临时 preload 仅观察真实 fs.watch 的创建、事件、错误
和关闭，不替换事件或写入行为。

失败 PID 69754、69756 的最后一个 scope 中，观察实例与写入实例的 watcher 6、7 均已
创建；两者随后 30 秒没有任何原生事件，也没有 error，最终在 dispose 时关闭。成功实例
则收到 JSON 文件的 rename 等事件。这不是单纯增加等待时间能够补发的事件。

仅改成 chokidar 并等待 ready 也不能关闭问题：24 轮中仍有 1 轮失败；加入阶段与原生
事件观测的后续 16 轮中有 5 轮失败，阶段均为「外部写入已经完成，等待外部通知」。
PID 92009、92188、92298、92506 的对应 scope 两个底层 watcher 均无事件；PID 92189
只有一个 watcher 收到 scope 目录自身名称的 change，未收到 JSON 文件事件。因此不能
把 ready 当作 Darwin 内核观察已经无缺口的保证，也不能只修改 JSON 文件名过滤便宣称修复。

临时目录别名的对照实验记录了原路径和 realpath：alias 组 16/16 完成，canonical 组
第 14 项仍在外部通知阶段达到原 30 秒超时。仅把 `/var` 改成 `/private/var` 不能解决。

与实测一致的上游记录：

- [Node #53111](https://github.com/nodejs/node/issues/53111)：Darwin 的 fs.watch 首次快速写入可能不产生事件，问题仍开放。
- [Node #52601](https://github.com/nodejs/node/issues/52601)：无法获知 macOS 原生监听真正开始的时间；该 issue 因长期无活动关闭，不能视为修复完成，讨论包含实体 Mac 复现。
- [libuv #3866](https://github.com/libuv/libuv/issues/3866)：FSEvents 的事件合并、起始事件过滤和 flush 行为，问题仍开放。

- `/tmp/mikiko-genui-native-69754.jsonl`、`/tmp/mikiko-genui-native-69756.jsonl`：原始 watcher ID 事件轨迹。

## 多 scope 开销实测

测量直接使用真实 storage 实现，准备 8 个 scopes，每个 scope 100 条持久记录。
基线、稳定空闲、dispose 后各采集 5 秒窗口；窗口计时仅用于测量，不参与监听初始化或
功能测试同步。准备完成与释放后在窗口之外请求 GC。证据：
`/tmp/mikiko-genui-polling-cost-final.log`，脚本为 `/tmp/mikiko-genui-polling-cost.mts`。

| 状态               | 实际窗口  | 用户 CPU | 系统 CPU | 单核 CPU 占用 | 活跃 uv polling handles | RSS      |
| ------------------ | --------- | -------- | -------- | ------------- | ----------------------- | -------- |
| 无观察者基线       | 5000.58ms | 2.404ms  | 0.461ms  | 0.057%        | 0                       | 120.8MiB |
| 8 × 100 条记录空闲 | 5000.71ms | 32.777ms | 98.123ms | 2.618%        | 808                     | 206.8MiB |
| dispose 后         | 5001.31ms | 7.530ms  | 0.508ms  | 0.161%        | 0                       | 206.2MiB |

808 是 `process.report.getReport().libuv` 中活跃的 **uv polling handles** 数量，
不是打开的文件描述符数量。每 scope 的 100 个记录与目录观察形成约 101 个 polling
handles；按 500ms 配置推算，8 scopes 约有 1616 次 metadata 采样/秒。这是依据配置
和句柄数的估计，没有通过系统调用追踪逐次计数。

三个窗口的 `process.resourceUsage()` 中 fsRead/fsWrite 增量均为 0，但该计数不覆盖
metadata stat，**不能据此称为零 IO**。CPU 百分比按进程 CPU 时间除以墙钟时间计算，
表示占一个逻辑核心的比例，不是整机 CPU 百分比。开销随持续观察的 scope/文件数量增长。

同一次测量中，程序内 set 在 5.12ms 返回，返回前已经收到 ACK 通知；另一实例提交的
外部快照在 314.24ms 被观察。这是单次延迟样本，不是分位数或最坏上限。

dispose 后 uv polling handles 从 808 降至 0，说明观察资源已回收；RSS 仍从基线
120.8MiB 保持在约 206.2MiB，没有回落到基线。本次没有 allocation profile，无法把
约 85MiB 的进程 RSS 高水位归因于 watcher、快照准备期间的分配、运行时缓存或其它
分配来源，也不能以 polling handles 归零宣称内存全部释放或不存在内存问题。
